# Stock-PM：离「动态 Investment Brain」还有多远（2026-09-23）

评估对象：`main`（9855e55）的代码，以及 2026-09-23 04:40 UTC 对生产环境 `http://43.166.2.31/` 只读 API 的实测。生产结果优先于代码和单测。

## 0. 一句话结论

**概念和数据结构大多已经有了，但闭环没有转起来。** 系统头重脚轻：推理层（`brain` + `research` + `decision` 约 4.7 万行）远厚于事实层；事实层又薄又慢，结果是上层 LLM 大部分精力花在写「证据不足以确定……」。生产上真正每天在跑、用户每天看到的，是另一套基于盘面规则的「环境 / 昨盘 / 预测」切片，不是 Brain。

## 2. 按目标逐层对照

成熟度分四档：**无** / **有结构**（有类型或表） / **能跑**（有代码路径，但生产上不跑或很少跑） / **生产有效**（每天在跑，而且输出可信）。

| 目标层 | 现状 | 成熟度 | 主要缺口 |
| --- | --- | --- | --- |
| Triage | `events/policy` 做来源分级；`brain/materiality` 用关键词门槛；`brain/constitution`、`hysteresis` 限制新闻直接改 Claim | 有结构 | 没有每条信息的分拣记录（类别、官方/传闻、生命周期、scope、冲击 vs 结构、最多传播到哪一层）；没有 `NOT_SEEN → … → STAGE4` 的传播轨迹，也就无法回答「为什么这条消息没有改变认知」 |
| Stage 1 事实 | Alpaca 行情可靠；FRED 与 AV 有健康码；官方 RSS / Atom；财报表 | 行情是生产有效，其余只算能跑 | 生产宏观全缺；没有 breadth 和成分股；新闻无时刻；SEC 每天一次；XBRL 数字没有进入事实层；采集器健康状态分散在 `sync_runs`、`job_runs`、`event_job_cursors`、进程内 `_STATE` 四处；`&&` 串联导致静默失败 |
| Stage 2 画像 | 生产版用约 20 只 ETF 代理（SPY、QQQ、IWM、SOXX、行业 SPDR、TLT、UUP、GLD、USO）算日涨跌和 5 日涨跌，再用规则识别现象 | 有结构 | 没有 breadth、factor、dispersion、concentration；没有按维度的状态和 provisional/confirmed；每天全量重算（Refresh = Recompute）；文字证据会过期而不自知 |
| Stage 3 推理 | 生产版的市场 driver 是固定模板，按 ETF 走势打分，带 `expected_signature`、`invalidation_conditions`、`validation_history`、`why_not_dominant`；个股层有规则生成的 `market hypotheses` | 能跑 | 「假设」其实是按价格打分的模板，Stage 2 和 Stage 3 混在一起；没有 counter / missing evidence / 未解释现象的系统化维护；不会发起 Research Request |
| Stage 4 认知 | `dominant_drivers` 在生产上为空；没有市场 Current View 对象 | 无 | 没有 Main View / Competing View / Previous → Current → 变化原因，也没有改变观点的门槛 |
| Company 知识与因果图 | `brain_states`、drivers、exposures、structural_paths 等表，以及 LLM 的公司理解 | 有结构（生产上仅 AVGO 一次） | 覆盖一只股票；没有持续更新；事实饥饿 |
| Core Claims | 3–5 条上限、版本历史、`hysteresis.next_claim_status`（单条新闻不能翻转、每次最多一档）、claim integrity 门禁 | 能跑 | 生产上只有 AVGO 一次运行；strongest counter 和 invalidation 大多为空；没有随新事实触发的状态转移 |
| Claim → 财务 → 情景 → 估值 → Thesis | 这些表和对象都有（`financial_impacts`、`scenarios`、`valuation`、thesis） | 有结构 | 财务影响量级未知；情景为空；估值不引用情景；没有 Thesis |
| Bridge | `ticker_sensitivities`、`structural_paths`、`price_attribution` | 有结构 | 市场 driver（ETF 模板）和公司 value driver（LLM 文本）没有共享 ID，穿透关系靠文字和主题标签对上 |
| Price Feedback | `brain/divergence`、`price_is_not_claim_invalidation`（原则正确）；研究问题会写入 `questions` | 能跑 | 生产的价格归因是「尚无价格归因证据」；研究问题只写不读，没有东西去执行，也就没有闭环 |
| Learning / Harness | 切片系统对价格边界做自动打脸（生产有效）；driver 有 `expected_signature` 和验证历史；有 benchmark、validate 脚本和 1000 多个单测 | 局部生产有效 | 打脸只覆盖技术面的短窗口预测，Brain 的判断没有进入评估；没有 calibration 统计；没有用生产历史做回放；harness 检查的是字段，不是能力 |

## 3. 根因（为什么会这样）

1. **没有单一可信的生产版本。** 线上代码不在仓库里；部署方式是从某台机器 `git archive` 过去。后面所有判断都建立在「线上跑的到底是什么」这个问题上。
2. **自上而下建造，事实层没有跟上。** 16 天、232 个提交、约 8 万行应用代码，大部分投入在 Brain 的阶段、门禁和对象上。事实层（宏观、带时刻的新闻、XBRL 数字、breadth）在生产上是空或慢的。上层再严谨，输入也只有「证据不足」。
3. **多套平行系统表达同一件事。** 同是「判断」，有切片预测、`research_*` 的 thesis、`brain_*` 的 claim/thesis、decision kernel 四处；同是「消息」，有 `news_articles`、`trusted_events`、外部检索文档、Brain news 四处。每一套都只做了一段，没有一套是完整闭环。
4. **没有持续运行的状态机。** Company Brain 是一次性 bootstrap；Market Brain 每天从 ETF 日线全量重算。「Refresh ≠ Recompute ≠ State Transition」目前没有载体：没有一个会随新事实被局部更新、并且留下转移记录的持久状态。
5. **反馈只写不读。** 研究问题、divergence、expected signature 都会产出，但没有消费方，所以学习和反馈是断开的。
6. **验证面向字段，不面向能力。** 单测很多，但生产上出现的问题（数字矛盾、噪声上位、宏观全缺、只有一只股票有 Brain）单测都没有拦住，因为测的是「字段存在、门禁生效」，不是「这一层是否真的完成了自己的职责」。

## 4. 应该重点解决什么（按顺序）

原则：**先做实下面，上面先冻结；先跑通一条窄而完整的纵向闭环，再横向扩展。** 纵向切片建议：1 个市场 + 3 家公司（AVGO、LITE、NVDA，覆盖 AI 半导体、光模块、GPU 这条产业链）。

### P0 生产治理（先做，别的都依赖它）

- 把线上正在跑的代码找回来、提交进仓库，和 `main` 对齐。之后只从 `main` 的 tag 部署，`/health` 返回 commit sha。
- 冻结新增 Brain 概念和新的平行对象；接下来的工作以「接通」和「删重复」为主。
- 建立一张统一的**生产真相面板**，由程序生成、不靠人看：每个采集器的最后成功时间和静默状态、每一层最后一次状态转移、每只股票 Brain 的新鲜度、当日数字自洽检查（例如同一标的同一日只允许一个涨跌幅）。

### P1 Stage 1 做实：让 Sensor Network 成立

- 按 N0 → N1 推进新闻层：日内调度、带时刻的主源（Alpaca News）、统一的数据源健康（已有 `stock_pm.news.health`），以及外部检索结果先入库。
- 修复生产宏观：查清 us2y、vix、wti、gold 为什么全部 missing；FOMC 和 CPI 的日程与结果改为从官方来源确定性写入，不再手工估计。
- **把 XBRL 和 10-Q 的数字接成事实**：分部收入、毛利率、营业费用、FCF、指引。这是解决 AVGO 那些 Claim「无法判断」的直接办法。
- 加上 breadth：用 Alpaca 批量快照计算一个固定成分集合（例如 S&P 500 或 Nasdaq-100）的涨跌家数、新高新低、等权与市值加权的差距，以及行业内离散度。
- 把 `sync_runs`、`job_runs`、`event_job_cursors`、进程内状态合成一个健康视图；daily service 去掉 `&&`，每一步都写 `job_runs`。

### P2 Triage 与传播轨迹（可解释性的主干）

- 每条进入系统的信息（新闻、公告、宏观发布、价格异动）写一条分拣记录：类别、官方/传闻/已验证、生命周期阶段、scope、冲击潜力 vs 结构潜力、是否需要验证、**最多允许传播到哪一层**。
- 同一条信息每向上走一层就追加一条轨迹：到了哪一层、那一层的结论是「改变 / 未改变 / 驳回」、原因。这张表同时回答「为什么变了」和「为什么没变」，也是后面 harness 的数据来源。
- 规则优先，LLM 只处理剩下的部分（与新闻层的分类顺序一致）；「最多允许传播到哪一层」是硬约束，由程序执行，不交给 LLM 判断。

### P3 Stage 2 市场画像成为持久状态

- 画像按维度存储（方向/breadth、领涨领跌、风格/因子、行业、跨资产、波动/信用/流动性、集中度/离散度），每个维度有自己的当前值、状态（provisional / confirmed）和变化历史。
- 新事实只重算受影响的维度；连续确认后才从 provisional 转为 confirmed。
- 画像只写「怎么走」；现在 driver 里夹带的「为什么」移到 Stage 3。

### P4 Stage 3 / 4：把市场 driver 模板升级为竞争性假设，再加上 Current View

- 现有 driver 已经有 expected signature、invalidation 和验证历史，这是很好的底子。需要补的是：support / counter / missing evidence、能解释和解释不了的现象（直接引用 Stage 2 的维度），以及生命周期。
- 缺证据时生成 Research Request：先查 Stage 1 的库，查不到再去外部检索，外部结果先入 Stage 1 再回来参与推理。
- Stage 4 新建一个很小的对象：Main View、Competing View、未解释结构、最大不确定性、Expected Future、Invalidation、Previous → Current → 变化原因。它只能在 P2 列出的五类条件满足时变化，并记录每一次「本来可能要变、但没有变」的评估。

### P5 Company Brain 持续运行（只做 3 家）

- 把增量 runtime 挂上定时任务，带预算：只有 Triage 允许传播到公司层、并且命中该公司某个 value driver 的新事实，才会触发对应 Claim 的重新评估。
- 强制链路完整：没有 financial impact 的 Claim 不能进入情景；估值必须引用 scenario id；数据不足时明确写 `unavailable`，而不是另外算一个目标价。
- Bridge 用共享 ID：市场假设和公司 value driver 之间用显式的 `driver_id` 关联，不靠主题标签匹配。

### P6 Price Feedback 闭环

- divergence 生成的 Research Question 进入一个有预算的执行队列，由 P1 的采集器和 P4 的 Research Request 去执行；问题有状态（open / 查证中 / 已回答 / 无法回答），回答结果以新事实的形式重新走 Triage。

### P7 Learning 与 Harness

- 统一的 Expected Signature：市场假设、Stage 4 观点、Company Claim、切片预测都写同一种「预期 → 到期 → 实际 → 评估」记录，由一个定时任务自动评估。
- 统计 calibration（按置信度分桶看命中率）、假阳性和假阴性、证据有用性、来源有用性。
- 回放 harness：把生产上每天的 Stage 1 快照保存下来，按天重放；验证的是能力，例如 Stage 2 是否没有去外部找事实、Stage 3 是否没有自己重组市场结构、Stage 4 是否只引用了 Stage 3 的对象。这些都能从 P2 的传播轨迹里机械地检查出来。
- 规则变更只以 Change Proposal 的形式存在，经过回放和盲测之后再升级版本。

## 5. 对现有部分的取舍

| 现有部分 | 建议 |
| --- | --- |
| 切片（environment / tape / prediction / review） | 保留为盘面观察和 Price Feedback 的输入，并把它的打脸机制扩展成 P7 的统一评估。它的短窗口方向性预测不再作为主判断展示，否则会和 Brain 形成两个互相竞争的结论 |
| `research_*`（Brain V1） | 作为 Company 事实和证据库的来源保留；thesis 和估值只在 `brain_*` 里维护，避免两处 thesis |
| `brain_*`（v2 各 Phase） | 作为 Company Brain 的主干；删掉只被 benchmark 或验证脚本使用的分支 |
| decision kernel | 看它的读方；如果只是一个视图模型，就并到 pm-view，不再单独维护一套判断 |
| `trusted_events` | 作为官方事实层并入 Stage 1；Triage 记录引用它的 `event_id` |

## 6. 每一步怎么算「做完」（以生产可观察为准）

| 步骤 | 验收（生产上能直接看到） |
| --- | --- |
| P0 | `/health` 返回的 sha 等于 `main` 的 tag；真相面板每天自动生成，没有数字自相矛盾 |
| P1 | 交易时段内新闻和 8-K 的入库延迟 ≤ 15 分钟；宏观序列全部 ok 或有明确原因；AVGO 最近一个季度的毛利率、分部收入以数字形式出现在事实层；breadth 每日可见 |
| P2 | 任取一条当日消息，都能查到它停在哪一层、为什么 |
| P3 | 画像的每个维度都有 provisional/confirmed 状态和变化历史；同一天内数值只有一个版本 |
| P4 | Market Current View 存在，有历史；「本来可能改变但没有改变」的评估有记录 |
| P5 | 3 家公司的 Claim 在出现新事实后自动重新评估，而不是只在 bootstrap 时生成；每条进入情景的 Claim 都有量级 |
| P6 | 至少一条研究问题完成「提出 → 查证 → 回答 → 以新事实回流」的全过程 |
| P7 | 每周自动产出 calibration 和来源有用性统计；至少一次规则变更走完 Change Proposal → 回放 → 升级的流程 |
