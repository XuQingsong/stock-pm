# 新闻层的四个核心问题：覆盖、分类、重要度、关联（2026-09-23）

承接 `NEWS_LAYER_N0_对接评估_2026-09-23.md`（数据源现状）和 `STOCK_PM_目标差距评估_2026-09-23.md`（P1 事实层、P2 Triage）。

## 0. 立场

这四个问题不是四个独立模块，而是同一个闭环里的四个环节：**拿到 → 认出是什么 → 判断有多重要 → 找到会波及谁**。每个环节都不可能靠一次写好的规则表解决，因为市场的主题、行业边界和传导路径一直在变（两年前没有 neocloud，也没人把消费级 AI 应用和 CPU 需求联系起来）。

所以每个环节都按同一个模式设计：

1. **静态起点**：规则、词典、先验，保证第一天能用；
2. **生产测量**：每个环节都有一个能从生产数据自动计算的误差指标；
3. **缺口驱动的探索**：误差和「解释不了的现象」自动生成研究问题，驱动检索；
4. **提议 → 验证 → 采纳**：探索的发现只能变成 Change Proposal（新来源、新分类节点、新先验、新关联边），经过历史回放验证后才生效。

这就是「动态」的具体含义：系统不是自己随意改规则，而是持续测量自己错在哪里，并按受控的流程修正。

## 1. 覆盖与实时：新闻源是否够多、够广、够快

### 1.1 按层设计来源，而不是按厂商

| 层 | 主要来源（免费或已有） | 实时方式 | 说明 |
| --- | --- | --- | --- |
| 公司 | **Alpaca News**：Benzinga 内容，带 `id`、UTC 的 `created_at/updated_at`、`symbols`；免费账号可用 WebSocket 推送；每天约 600–900 条标题 | 推送 | 公司层的主源；key 已经有了 |
| 公司 | SEC EDGAR：8-K、6-K、Form 4、13D/G、S-1 | 每 1–2 分钟轮询，公平访问上限约 10 次/秒 | 一手事实，按 accession 去重 |
| 公司 / 行业 | 新闻通稿 RSS：PR Newswire、Business Wire、GlobeNewswire，都有**按行业分类的 feed** | 每 1–2 分钟轮询，配合 ETag | 公司 IR 发布几乎都走这三家，比 IR 网站快，而且自带行业标签 |
| 公司（备用源） | Alpha Vantage NEWS_SENTIMENT、Finnhub company-news（免费 60 次/分钟）、Nasdaq | 5–15 分钟 | 交叉召回，用来衡量主源漏了什么 |
| 行业 | 行业媒体 RSS：存储（TrendForce 等）、光通信（Lightwave 等）、数据中心 / neocloud（Data Center Dynamics 等）、硬件（Tom's Hardware 等）、AI 与软件（TechCrunch 等） | 5–15 分钟 | **行业层是最难的一层**：厂商 API 以 ticker 为中心，行业动态主要在行业媒体和行业数据发布里 |
| 行业 | 行业数据发布：DRAM/NAND 合约价、SIA 月度芯片销售、SEMI 设备出货、电话会里的行业表述 | 按发布日程 | 这些是结构化事实，用程序直接解析，不交给 LLM |
| 宏观 | 官方：Fed 声明 / 讲话 / 会议纪要、BLS / BEA 发布日程、Treasury 拍卖结果、EIA 周度库存、OPEC、OFAC 制裁、商务部 BIS 出口管制 | 按日程加轮询 | 日历事件按确定性事件键生成（如 `fomc:2026-09-16`），结果写入后与预期比较 |
| 宏观 / 地缘 | **GDELT 2.0**：免费，每 15 分钟更新，覆盖全球百余种语言媒体，事件带类型编码、地点和参与方 | 15 分钟 | 战争、制裁、冲突升级这类事件的广覆盖来源；只用来发现和计量升级，不当作事实本身 |
| 宏观 / 市场 | 媒体 RSS 标题：CNBC、MarketWatch 等分栏目 feed | 5 分钟 | 头条广度 |
| 另类信号 | App Store 榜单（Apple 官方公开 JSON，免费）、Google Trends 等 | 1 小时 | 往往先于新闻出现，例如一款应用冲上榜首 |
| 补漏 | Tavily / Exa（已接入） | 按需 | 只在缺口驱动时调用，结果先入库再使用 |

实时的关键不是来源数量，而是**每个来源都有明确的时效目标**，并由 `news.health` 监控：推送类以秒计，一手源和通稿不超过 2 分钟，行业媒体不超过 15 分钟，GDELT 不超过 30 分钟。

### 1.2 怎么知道覆盖够不够

来源再多，也不能证明没有漏。需要三个能自动计算的指标：

1. **未解释异动率**（最重要）：对自选股和各行业篮子，在事件窗口内出现异常收益（扣除大盘和行业的 beta 之后）时，如果找不到关联的 story，就记一次覆盖缺口。按层统计这个比例，它直接衡量「市场知道、我们不知道」的程度。
2. **交叉召回**：主源和备用源在同一个 ticker 上各自抓到的 story，重叠比例是多少。一个源独有的 story 越多，说明另一个源漏得越多。
3. **主题扫描召回**：每天对每个行业节点用检索做一次扫描（例如「HBM 价格」「光模块 800G 订单」），检查搜到的 story 有多少已经在库里。

每个缺口都会生成一个研究问题：定向检索找到这条新闻 → 记录它来自哪个域名。**某个域名反复提供我们漏掉的早讯时，自动提议把它加入来源表。** 来源表就是这样动态长大的。

### 1.3 付费升级的优先顺序

先把免费源接满、跑出上面三个指标，再看缺口集中在哪一层，决定是否付费：公司层缺口大就上 Benzinga 全量或 Polygon；行业层缺口大就上专业行业数据；宏观层缺口大就上经济日历和一致预期。

## 2. 分类：是什么新闻、影响谁

### 2.1 分类不是单个标签，而是几个独立维度

| 维度 | 取值 | 例子（Meta 的 Muse 登顶 App Store） |
| --- | --- | --- |
| 事件类型 | `config/news_taxonomy.yaml` 的三级类别 | 产品 / 用户数据 / 应用排名 |
| 层级（scope） | single_entity / industry / multi_industry / market_wide / macro / systemic | single_entity（起初） |
| 主体实体 | 这条新闻**说的是谁** | META |
| 提及实体 | 文中出现但不是主角的 | OpenAI、Google |
| 影响节点 | 宏观因子或行业树节点 | 消费级 AI 应用 |
| 状态 | rumor / official / verified；proposed → effective | official（榜单是事实） |

「主体」「提及」「受影响」必须分开存。受影响的范围是第 4 节关联要回答的问题，不在分类阶段猜。

### 2.2 分类依赖的三份基础数据

- **公司实体库**：以 SEC `company_tickers.json` 为骨架（研究链路里已经在用），补充别名、产品名（Muse → META，HBM → 存储）、子公司、高管（CEO 的讲话归到公司）、ADR 和多类股映射，以及容易混淆的 ticker 规则。
- **行业树**：按你的关注范围定制，每个节点有描述、关键词和**成分股篮子**。示意：
  - 半导体：存储（MU、SK Hynix、SNDK、WDC）/ GPU 与加速器 / CPU（INTC、AMD、ARM）/ 定制芯片（AVGO、MRVL）/ 设备 / 代工
  - 光通信：光模块（LITE、COHR、AAOI、FN）/ 网络设备
  - 硬件与数据中心：服务器 / 电源散热 / neocloud（CRWV、NBIS 等）
  - 软件：基础模型与 AI 平台 / SaaS / 网络安全
  - 消费：消费电子 / 互联网平台 / 零售
  - 金融：银行 / 券商 / 保险
  - 能源与原材料：油气 / 黄金白银 / 工业金属

  篮子要同时用于分类（识别行业）和价格反应计量（第 3、4 节），所以篮子成分股的行情也要采集（对应差距评估 P1 的 breadth）。
- **宏观因子表**：利率（2Y / 10Y）、美元、原油、黄金白银、VIX、信用利差、通胀、就业、增长、地缘风险，每个因子对应可观测的市场序列。

### 2.3 分级流水线

1. **一手元数据**：8-K Item、经济日历、通稿的行业标签、厂商 `symbols`，直接采用。
2. **规则和词典**：实体库和行业树的精确匹配。
3. **向量近邻**：与已标注样本比较相似度，处理措辞多变但语义明确的情况。
4. **LLM**：只处理前三步置信度不够的部分。输出必须从给定的 ID 列表里选，并引用原文片段作为依据，不允许自由发挥标签。
5. **低置信度进复核队列**：每天最多 10 条请你确认，确认结果回灌样本库。

### 2.4 准确率怎么测

- 建一个金标集：按层分层抽样 300–500 条 story，人工标注各维度。
- 每周自动报告各维度的精确率和召回率，其中**实体链接**（主体是否正确）单独统计。
- 抽样对比 LLM 结果和规则结果，分歧大的类别优先补样本或补规则。

### 2.5 动态部分：分类体系自己长大

- 持续对「未能归类」的 story 聚类。一个簇足够密、持续出现，而且有价格反应时，提议新增行业节点或主题（neocloud、agentic CPU 就是这样出现的）。
- 新节点走 Change Proposal：用历史 story 回放，确认它确实能把原来无法归类的新闻正确分进去，并且不会抢走其他节点的正确样本，然后才生效。

## 3. 重要度：哪些是大事，哪些影响有限

### 3.1 重要度 = 事件强度 × 与当前认知的相关度，再加上演化

**事件强度**（沿用 docs/08 的公式）：（类型先验 + 意外幅度 + 主体规模 + 影响广度）× 新颖度 × 可信度，分为 P0–P3，并用硬规则兜底（例如 FOMC 决议、CPI 发布不低于 P1）。

**与当前认知的相关度**，这是把「重要」和「显眼」区分开的关键：这条新闻是否触及 Market Brain 当前主假设的支持、反证或失效条件，或者某家公司 Core Claim 的验证节点。触及失效条件的新闻，即使措辞平淡，也应该升级。

**演化**：重要度挂在 story 上，而不是单篇文章上。同一件事持续升级时（冲突扩大、参与方增加、波及能源设施），story 的重要度会随时间线变化。

### 3.2 用你的例子来看

| 新闻 | 事件强度 | 相关度 | 结果 |
| --- | --- | --- | --- |
| AI 大模型研发放缓 | 类型先验中等；可信度看来源（传闻 vs 公司确认） | **直接命中「AI capex 持续增长」这个主假设的失效条件**，并波及 AVGO、NVDA、LITE 的 Core Claim | P0（官方确认时）；传闻阶段为 P1 并标记需要验证 |
| 美伊战争加剧 | 先验高；按升级阶梯细分：言辞 → 制裁 → 局部冲突 → 能源设施 / 霍尔木兹海峡 → 多方卷入，每一级有自己的先验 | 命中原油、黄金、避险、通胀这些宏观因子 | 按阶梯 P2 → P0；GDELT 的事件计数和媒体覆盖面用来确认是否真的在升级 |
| 美联储加息 | 日历事件，先验高；**意外幅度**要和事先的市场隐含预期比较 | 命中利率因子，以及所有高估值成长股 | 符合预期时为 P1（事件已被定价）；意外时为 P0 |
| CEO 出席活动发表讲话 | 默认 P3 | 只有内容里出现新数字、指引，或者与某条 Core Claim 相关的新事实时才升级 | 通过内容抽取有条件升级，而不是看「谁讲的」 |

### 3.3 怎么让重要度越来越准

- **LLM 评分必须使用锚定量表**：每一档配 3–5 个参照案例，输出必须说明依据的是公式里的哪几个分量，不允许直接打一个分数。
- **事后校准**：对每个 story，用事件研究法计算事后反应，包括相关资产的异常收益、成交量和波动率变化，以及受影响篮子的范围。定期统计「类型先验」和「事后反应」的偏差，以 Change Proposal 的形式调整先验，回放验证后生效。
- **价格反应不实时回写重要度**（docs/08 的原则）。它只用于排序、审计和校准先验；否则重要度会变成「涨得多就重要」，失去独立判断。
- 两个指标：**重要度等级与事后反应的秩相关**；**P0 漏报率**，即大异动当天最高等级的 story 却只有 P2 或 P3 的比例。

## 4. 关联：新闻之间、新闻与行业之间的联动

### 4.1 关联有三种来源

1. **结构关联（知识图谱）**：供应链、客户、竞争对手、产品、主题篮子、因子暴露。来源包括 10-K 里的客户集中度和供应商披露、电话会、行业报告，以及 LLM 从文档里抽取的关系（每条边必须带出处）。
2. **叙事关联**：多个 story 汇聚成一条更长期的叙事（例如「AI agent 拉动 CPU 需求」「HBM 紧缺」）。叙事有成员 story、强度（story 数量、来源多样性）、价格确认程度，本身就是 Market Brain Stage 3 假设的原材料。
3. **经验关联（反应共振）**：在 story 的反应窗口里，看哪些篮子出现了超出 beta 的异常波动。这是发现「我们还没建模的关联」的主要途径。

### 4.2 用 Muse 的例子走一遍

1. Muse 冲上 App Store 榜首：榜单信号先到，新闻随后到；分类结果是主体 META、节点「消费级 AI 应用」。
2. 结构图谱里只有 META 这一条关系，所以影响面预测只有 META。
3. 当天 CPU 篮子（INTC、AMD、ARM）出现异常上涨，同时没有 CPU 自身的新闻。系统记录一次**未解释共振**：story = Muse，篮子 = CPU。
4. 自动生成研究问题：「CPU 板块为什么和 Muse 同时上涨？」然后定向检索，找到市场叙事，例如 agent 类应用在推理之外有大量调度和工具调用，更依赖 CPU。
5. 提议新的关联边：「消费级 AI agent 放量 → CPU 需求」，状态为 **假设**，并附上检索到的证据。
6. 之后再出现同类 story（其他 agent 应用放量、CPU 厂商提到 agent 负载）时，系统先**预测** CPU 篮子会有反应，再看实际结果。命中若干次后，这条边升级为 **已验证**；持续不命中就逐渐衰减并退出。

这个例子就是整个系统「动态探索」的最小单元：**现象解释不了 → 提出问题 → 检索 → 提出关联假设 → 用后续事件检验 → 采纳或淘汰。**

### 4.3 约束

- 价格共振只用来**发现关联假设**和**检验关联**，不直接修改某条 story 的重要度，也不直接修改公司的 Claim；这与「价格只引出研究问题」的原则一致。
- 关联边有状态：hypothesis → validated → decaying。只有 validated 的边能用于实时影响面扩展，hypothesis 的边只用来生成「待观察」提示。
- 指标：**影响面预测的精确率和召回率**（预测受影响的篮子 vs 实际异常的篮子），以及每月新发现并验证通过的关联边数量。

## 5. 四个环节合起来的动态闭环

```
来源 ──► 标准化 / 去重 (N0) ──► story 聚类 ──► 分类 ──► 重要度 ──► 关联扩展 ──► Triage ──► Market / Company Brain
  ▲                                                                                          │
  │                           未解释异动 · 交叉召回缺口 · 未归类簇 · 未解释共振 · P0 漏报    ◄──┘ 价格反应（只用于测量）
  │                                           │
  └──── 新来源 / 新节点 / 新先验 / 新关联边 ◄── Change Proposal ◄── 回放验证 ◄── 研究问题 → 定向检索（结果先入库）
```

探索需要预算：每天有固定的检索次数和 LLM token 上限，按缺口的严重程度排序使用。优先处理 P0 漏报和持仓标的的未解释异动。

## 6. 在 stock-pm 里的落地顺序

| 阶段 | 做什么 | 复用什么 | 生产上怎么验收 |
| --- | --- | --- | --- |
| N1 来源与实时 | 接入 Alpaca News 推送、通稿 RSS、SEC 1–2 分钟轮询、GDELT、App Store 榜单；建立来源表和覆盖矩阵；日内调度 | `news.adapters`、`news.health`、`events.feeds`（ETag、限速） | 各来源的延迟达标；三个覆盖指标每天产出 |
| N2 分类 | 公司实体库、行业树和篮子、宏观因子表；分级流水线；金标集；复核队列 | `research/live_fetch` 的 SEC ticker 表、`config/news_taxonomy.yaml`；替换 `impact.tag_news` | 金标集上各维度的精确率和召回率周报 |
| N3 story 与重要度 | 确定性事件键加向量聚类；强度 × 相关度；升级时间线；锚定量表 | `trusted_events` 作为官方事实层；Brain 的假设和 Claim 作为相关度的参照 | 秩相关和 P0 漏报率周报 |
| N4 关联与探索 | 知识图谱边（带出处和状态）；事件研究法计量；未解释共振 → 研究问题 → 检索 → 关联提议 | `brain/divergence` 的价格背离、`brain_research_questions`、`external` 检索、`brain_change_proposals` | 影响面预测的精确率和召回率；至少一条关联边走完「发现 → 验证 → 采纳」 |

N1 和 N2 可以并行推进；N3 依赖 N2 的实体和行业；N4 依赖 N1 的时刻精度和篮子行情。
